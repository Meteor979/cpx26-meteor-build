# WearWise 页面流程草案

## 1. 产品与前端边界

WearWise 帮助大学生从已经拥有的衣物中，为具体场合选择三套可解释的搭配。

前端负责：

- 接收自由文本场合搜索，并展示解析后的策略供用户确认。
- App 启动时自动申请定位权限、读取粗略位置和当地天气。
- 将天气作为后台结构化上下文，并收集正式程度和衣物。
- 引导用户拍摄并确认衣物特征。
- 展示识别、匹配、生成和错误状态。
- 在接口失败时使用本地 MockData。
- 保存已确认衣物、预设和推荐结果缓存。

后端负责：

- 预计算常用场合策略，并解析自由文本场合。
- 根据授权后的粗略位置查询天气。
- 识别图片中的结构化衣物特征。
- 根据标签和外观查找商品候选。
- 使用正式程度分层和规则生成候选搭配。
- 使用可替换 AI Provider 排序和生成解释。
- AI 失败时返回规则 fallback。

图片默认保存在设备本地。图片识别时上传经过压缩的临时图片；后端不得长期保存。

## 2. 信息架构

```text
首页
├─ 场合搜索框
├─ 常用/最近场合建议
├─ 我的衣柜状态
└─ 进入我的衣柜

我的衣柜
├─ 添加衣物
│  ├─ 方式一：AI 识别衣物特征
│  └─ 方式二：标签与外形品牌匹配
├─ 查看/编辑衣物
└─ 选择本次可用衣物

推荐
├─ 生成中
├─ 三套搭配
├─ 搭配详情
├─ 替换单品
└─ 最终方案
```

## 3. 首屏启动

### 目标

先建立必填的本地天气上下文，再让用户输入场合并开始。

### 启动时数据

按以下顺序加载：

1. 读取最近输入、场合策略缓存和允许使用的最近天气。
2. 检查定位权限。
3. 未授权时请求“使用 App 期间”的粗略定位权限。
4. 获取一次位置并调用 `POST /v1/weather/current`。
5. 天气上下文准备好后进入首页。
6. 后台请求 `GET /v1/presets` 更新搜索建议。

### 页面内容

```text
WearWise
今天是什么场合？

[ 输入：社团演讲、实习面试、朋友生日聚餐……   搜索 ]

常用：初次约会 · 社团演讲 · 沙龙表演

已有 8 件衣物 · 3 套可直接搭配
[管理衣柜]
```

首页不显示独立天气卡片。天气、体感温度和降雨概率只作为内部结构化特征，用于
推荐规则和最终解释。

搜索框是首页的主要操作，不能把预设置于视觉中心。预设只用于：

- 搜索时的匹配建议。
- 用户没有输入时的短快捷项。
- 后端生成自定义策略时的参考模板。

### 搜索建议

- 输入框获得焦点后再显示建议，默认最多四条。
- 优先显示最近使用的场合、常用预设和模糊匹配结果。
- 点击建议只填入搜索框，不直接跳到推荐页。
- 用户仍需确认解析后的正式程度，天气由系统自动提供。
- 空输入时显示短快捷项；页面主标题保持为场合输入语句。

### 定位与天气

位置权限是进入主流程的必需权限。系统权限提示前先显示用途说明：
“用于自动获取当地温度和降雨情况，不保存精确位置或定位轨迹。”

前端状态：

```text
app_launch
  → permission_check
  → permission_requesting
  → location_resolving
  → weather_loading
  → context_ready
  → home

permission_requesting
  → permission_denied
  → blocking_permission_screen

weather_loading
  → weather_failed
  → blocking_weather_screen
```

权限规则：

- App 启动时自动检查并请求定位，不提供跳过入口。
- 使用“使用 App 期间”权限和粗略位置，不要求精确位置。
- 经纬度保留到适合天气查询的粗粒度，不建立位置历史。
- 用户拒绝或系统限制定位时，显示阻塞说明页和“前往系统设置”。
- 天气接口失败时优先使用 60 分钟内缓存；没有可用缓存则显示重试页。
- 不提供手动温度输入。
- 天气不显示为首页卡片，但调试构建可以显示只读状态。

iOS 实现要求：

- 只配置 `NSLocationWhenInUseUsageDescription`，不申请后台定位。
- 使用 `CLLocationManager`，目标精度约为公里级。
- 使用一次位置结果立即查询天气，不持续追踪。
- 每次冷启动自动刷新天气；前台长时间停留时不需要持续轮询。

## 4. 场合搜索与解析

### 状态

```text
idle
  → typing
  → suggesting
  → resolving
  → profile_ready
  → wardrobe_check
```

### 交互

- 输入框支持自由文本，例如“第一次去女朋友家吃饭”。
- 输入期间仅做本地模糊搜索，不在每个按键上调用远端 AI。
- 用户点击搜索或按回车后提交完整查询。
- 提交后先自动匹配内置和已经缓存的场合策略。
- 本地匹配成功时立即进入确认页，不调用 AI。
- 本地没有达到匹配阈值时，才调用 `POST /v1/occasions/resolve`。
- 解析成功后显示目标正式程度、风格关键词和避免项。
- 用户可修改解析后的正式程度，天气保持自动获取的结构化上下文。
- 如果衣柜缺少上装、下装或鞋子，跳转衣柜并显示缺失项。
- 如果衣柜完整，进入衣物选择或直接生成。

### 本地优先匹配

匹配顺序固定为：

```text
规范化输入
  → 精确名称
  → 同义词/别名
  → 关键词和字符相似度
  → 本地达到阈值：直接使用
  → 本地未达到阈值：调用 AI
```

输入先做轻量规范化：

- 去除首尾空格和连续标点。
- 统一中英文标点、大小写和全角/半角字符。
- 将“第一次约会”等常见表达映射到规范化别名。

内置预设应带别名：

```text
初次约会：
  第一次约会、首次约会、初次见面的约会

结婚纪念日约会：
  纪念日、周年约会、结婚纪念日

沙龙表演：
  沙龙、演奏会、节目演出、小型演出

社团演讲：
  社团汇报、社团分享、社团路演
```

本地匹配可以使用精确名称、别名、关键词包含和简单编辑距离，不需要在手机上运行
大型模型。建议命中阈值：

```text
精确名称/别名：直接命中
关键词覆盖率 >= 0.75：直接命中
综合相似度 >= 0.80：直接命中
低于阈值：调用 AI
```

阈值和别名表使用应用版本控制。AI 返回的新策略经过用户确认后写入本地策略缓存，
同时保存规范化输入和别名，下一次相同或相近输入优先走本地匹配。

场合确认示例：

```text
“第一次去女朋友家吃饭”

理解为：偏休闲的家庭聚餐
建议正式程度：智能休闲
重点：干净、自然、不过分正式
自动天气：16°C，降雨概率 20%

[修改正式程度] [继续选择衣物]
```

规范化查询与策略缓存在本地：

```text
key: normalized_occasion_query + locale
value: OccasionPreset
invalidate: version changed or user edits policy
```

已确认的 AI 生成策略也加入同一索引，但在当前会话中仍保留 `generated` 来源标记。

### 失败处理

- 本地已有相同查询策略：直接使用，不调用后端。
- 本地内置预设达到阈值：直接使用，不调用后端。
- 远端解析失败：使用关键词和最近预设生成通用策略，并标记来源。
- 解析置信度低：只建议正式程度，要求用户确认。
- 无网络：允许从最近使用和常用场合进入，也允许手动选择正式程度。
- 查询为空：不提交，只显示建议。

## 5. 我的衣柜

### 空状态

```text
还没有可以搭配的衣服

先拍摄衣物照片。照片会保存在这台设备上。

[添加第一件衣物]
[载入演示衣物]
```

“载入演示衣物”仅供断网演示和评审快速体验，正式流程仍以用户拍摄为主。

### 正常状态

衣物按槽位分组：

```text
上装
  浅蓝牛津衬衫
  米白针织衫

下装
  深蓝直筒牛仔裤
  黑色西裤

鞋
  白色运动鞋
  棕色乐福鞋
```

每件衣物可以显示：

- 本地缩略图。
- 正式程度标签。
- 保暖程度。
- 识别状态：`手动录入`、`AI 已识别`、`品牌匹配`、`待重试`。
- 是否存在来源商品页。

## 6. 添加衣物入口

点击添加后显示两个明确选项：

```text
选择识别方式

方式一：快速识别
拍一张衣物照片，AI 建议类别、颜色、正式程度等，
由你逐项确认。

方式二：品牌匹配
拍摄衣物外形和标签，读取品牌与货号，
联网查找商品候选。
```

两种方式最终都进入同一个“确认衣物”表单。

## 7. 方式一：AI 识别衣物特征

### 流程

```text
capture
  → compressing
  → analyzing
  → reviewing
  → saving
  → indexed
```

### 拍摄

- 首选相册或相机入口。
- 提示用户使用纯色背景、保持衣物完整入镜。
- 只要求一张正面照。
- 背面、材质细节和标签为可选补充照片。
- 客户端压缩图片并裁掉明显无关区域。

### 识别中

- 显示进度和“可随时转手动录入”。
- 超过 10 秒显示取消按钮。
- 用户离开页面时取消未完成请求。

### 审核页

识别结果只作为建议值：

```text
确认衣物信息

槽位
  (●) 上装   ( ) 下装   ( ) 外套   ( ) 鞋

类别
  [衬衫 v]

颜色
  [浅蓝] [+ 添加颜色]

正式程度
  1 休闲  [2]  [3]  4 正式

保暖程度
  1 很薄  [2]  [3]  4 保暖

版型和图案
  常规版型 / 纯色

材质
  棉  · 低置信度，请确认

[重新拍摄] [保存到衣柜]
```

### 规则

- 用户选中的值覆盖 AI 建议值。
- 低置信度字段不能自动通过。
- `slot`、`category`、颜色、正式程度和保暖程度必须确认。
- 保存时计算正式程度层并创建立即检索索引。
- AI 失败时保留本地照片，转为空白手动表单。

正式程度映射必须前后端一致：

```text
formality_score 1–2 → casual
formality_score 3   → smart_casual
formality_score 4   → business
formality_score 5   → formal
```

`formality_band` 是派生值。推荐请求只发送 `formality_score`，由后端重新计算层级，
防止客户端提交互相冲突的分数和层级。

## 8. 方式二：标签和外形品牌匹配

### 流程

```text
appearance_photo
  → label_photo
  → ocr
  → text_review
  → appearance_analysis（可选）
  → matching
  → candidate_selection
  → attribute_review
  → saving
```

### 拍摄页

要求拍两张：

1. 衣物整体外形。
2. 吊牌、洗标或条形码。

标签照片优先在本机 OCR。默认只上传识别出的文字，不上传整张标签图。

如果用户希望按外形搜索相似款，客户端先调用图片分析接口取得结构化外观字段，
再把外观照片压缩成较小的缩略图，通过 `appearance_image_base64` 发送给匹配接口。
图片只用于本次搜索，不写入缓存，也不得长期保存。

如果赛事搜索能力不支持图像相似搜索，则使用结构化外观字段做相似款搜索，并在
结果页标明“按属性匹配”，不能显示成“图片识别完全一致”。

### 标签审核

```text
请确认标签文字

品牌：UNIQLO
商品名：Oxford Shirt
货号：123456
材质：100% Cotton

[编辑文字] [开始查找]
```

用户可以删除 OCR 错误，也可以直接粘贴商品链接或输入品牌和货号。

### 商品候选页

最多展示三个候选：

```text
找到可能的商品

候选 1 · 高匹配
UNIQLO
Oxford Shirt · 浅蓝
匹配依据：品牌、货号、颜色
[查看来源] [这是这件]

候选 2 · 相似
[查看来源] [这是这件]

[都不是，转为手动录入]
```

界面不得使用“正版已确认”。只使用：

- `精确商品匹配`
- `可能的商品`
- `相似款`
- `未找到商品`

用户选择候选后，商品页提取的属性仍进入统一审核页，用户可以修改。

### 失败处理

- OCR 失败：保留照片，转为手动输入标签。
- 搜索无结果：保留标签字段，转手动录入。
- 网络失败：保存标签文字，允许稍后重试。
- 商品页读取失败：保留候选名称和来源链接，不能编造缺失字段。
- 商品网址只允许 HTTPS；后端必须拒绝 localhost、内网地址和云元数据地址。

## 10. 推荐生成

### 前端状态

```text
idle
  → loading
  → success
  → fallback
  → error
```

### 加载页

- 显示简短步骤，例如“检查正式程度”“组合现有衣物”。
- 防止重复提交。
- 10 秒后提示网络较慢。
- 15–20 秒后取消远端请求并使用本地 Mock。

### 请求前

只发送已经由用户确认的衣物结构数据，不发送衣物照片。

推荐请求必须携带启动时自动取得的温度、体感温度、天气状况、降雨概率和风速。
下雨或强风时可提高封闭鞋和外套的优先级。

### 失败顺序

```text
远端 API
  → 后端规则 fallback
  → 前端本地 MockData
```

任何一层成功都进入推荐结果页，并显示对应来源标签。

## 11. 三套搭配页

每套搭配使用一张卡片：

```text
方案 A · 清晰但不过分正式

[衬衫] [西裤] [乐福鞋]

为什么适合
· 符合初次约会的智能休闲正式程度
· 浅蓝与深色下装形成稳定对比
· 适合 16°C 的轻外套搭配

取舍
· 比运动鞋略正式

[查看详情]
```

结果页操作：

- 左右滑动或纵向浏览三套方案。
- 进入详情。
- 替换单品。
- 确认其中一个方案。
- 重新生成。

最多三套，不允许无限滚动。

正常情况必须返回三套。候选组合不足时允许少于三套，但响应必须通过
`result_count_reason` 说明原因，页面显示“仅找到 2 套”等提示，不能静默少返回。

## 12. 搭配详情与单品替换

详情页展示：

- 整套搭配。
- 每件衣物的角色。
- 推荐理由。
- 风险/取舍。
- 来源标签。

替换规则：

- 只显示同一槽位的候选衣物。
- 用户已经选择的其他单品保持锁定。
- 优先调用 `POST /v1/outfits/revise`，保持其他单品不变并重新生成理由。
- 替换接口失败时，在前端更新组合，并明确标记“手动调整”。
- 不继续显示可能已经失效的 AI 推荐理由；改为显示基于正式程度和保暖程度的模板理由。

## 13. 最终确认

```text
已确认方案 A

场合：初次约会
天气：16°C
搭配：浅蓝衬衫 + 深蓝牛仔裤 + 白色运动鞋

[保存为今日方案]
[继续调整]
```

确认后保存：

- 搭配 ID。
- 衣物 ID。
- 场合和天气。
- 推荐来源。
- 保存时间。

下一次打开时可以直接查看，不重新生成。

## 14. 本地缓存

### 场合建议与解析策略

```text
keys:
  presets (搜索建议)
  occasion_profile:<normalized_query>:<locale>
invalidate: version changed
```

最近输入只在用户设备保存，并允许用户清空搜索历史。

### 天气

```text
key: weather_context:<rounded_location>:<date>
value: WeatherData + location_label + observed_at
invalidate: 30–60 minutes
```

天气缓存可以保留粗粒度地点名，但不能保存连续定位轨迹。

### 已确认衣物

```text
key: wardrobe
revision: increases after add/edit/delete
```

### 商品匹配

```text
key:
  match_mode
  + normalized_label_hash
  + brand
  + product_code
  + appearance_fingerprint
invalidate: stale after 7 days or manual refresh
```

`appearance_fingerprint` 使用本地生成的外观哈希或视觉特征摘要，不要缓存原始标签图。

### 推荐结果

```text
key:
  preset_id
  + formality_band
  + temperature_bucket
  + wardrobe_revision
  + selected_garment_ids_hash
```

温度建议分桶为 `cold / mild / warm`，不要为每一个温度数值创建缓存。

缓存键由客户端计算，不从后端读取。建议边界固定为：

```text
cold:  低于 10°C
mild:  10–22°C
warm:  高于 22°C
```

后端不接收 `wardrobe_revision`；衣物变化时由客户端提升 revision，使旧缓存失效。

## 15. 全局错误和断网状态

统一使用非阻断提示，除非用户无法继续当前操作。

| 场景 | 前端行为 |
|---|---|
| 预设接口失败 | 使用本地预设 |
| 场合解析失败 | 使用关键词、最近策略或手动正式程度 |
| 定位权限被拒绝 | 显示阻塞说明和“前往系统设置” |
| 定位权限受系统限制 | 显示不可用说明，不进入推荐流程 |
| 天气接口失败 | 使用 60 分钟内缓存；没有缓存时显示重试页 |
| 图片识别失败 | 保留照片，转手动录入 |
| 识别超时 | 允许取消并转手动录入 |
| 标签搜索失败 | 保留 OCR 文字，允许重试或手填 |
| 商品页不可访问 | 保留候选名称与 URL |
| 推荐接口失败 | 使用本地 MockData |
| 后端 fallback | 正常展示，并标记来源 |
| 图片过大 | 客户端自动压缩后重试一次 |
| 重复点击 | 请求期间禁用按钮 |
| 非法衣物 ID | 丢弃响应并进入 fallback |

## 16. 公开网页 Demo

公开网页只复刻核心流程：

```text
输入场合并确认解析结果
→ 自动载入固定 Mock 天气
→ 从样例衣柜勾选衣物
→ 展示三套搭配
→ 查看理由
→ 替换一件
→ 确认搭配
```

网页默认使用静态 Mock 数据和固定天气，不请求浏览器定位，也不提供完整图片识别
上传。它必须与 iOS 使用相同的场合策略、天气结构、衣物和推荐字段，明确标注为
交互式原型。

## 17. 验收路径

现场至少连续完成三次：

1. 冷启动 App。
2. 授权粗略定位并自动取得天气上下文。
3. 在搜索框输入“第一次去女朋友家吃饭”。
4. 确认解析出的正式程度和自动天气上下文。
5. 使用已有衣柜生成三套搭配。
6. 查看一套详情。
7. 替换一件同槽位衣物。
8. 确认并保存。
9. 关闭后端，再次完成推荐。
10. 添加一件衣物，验证 AI 失败后可以手动保存。
