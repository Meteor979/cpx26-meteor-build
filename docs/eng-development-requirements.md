本文件是产品和工程的详细开发基线。[CONTRIBUTING.md](../CONTRIBUTING.md)
仍是角色、分支、提交和权限的唯一权威。接口字段以

## 1. 产品定义

WearWise 衣语面向色盲、色弱和低视力用户，从用户拍照建立的本地衣柜中推荐
三套可解释搭配，并以黑白高对比、大尺寸图形界面完成选择、替换和确认。

产品必须回答：

```text
今天穿什么，为什么这套适合我？
哪三套适合当前场合，它们分别是什么感觉？
```

产品不是简单的颜色分类器，也不是只输出文字理由的推荐器。推荐结果必须用
用户自己拍摄的衣物图片组成真实搭配，帮助用户确认系统没有使用错误的衣物。

全盲用户不在本次目标范围。用户可以看见衣物和界面，能够拍照建立衣柜，
但可能难以辨别颜色、细节或低对比度界面元素。

## 2. 用户与核心价值

目标用户：

- 红绿色弱、蓝黄色弱或其他色觉辨别困难的用户。
- 需要大字号、高对比度、稳定边框和更少视觉层级但仍能触摸操作的低视力用户。
- 能够拍照、管理自己的衣物，但难以独立判断搭配是否协调的用户。

必须满足：

- 通过清晰、可点击、图标加文字的图形按钮完成核心流程。
- 不依赖颜色区分选中、禁用、警告和错误状态。
- 推荐结果展示用户衣柜中的真实衣物照片。
- 推荐理由不仅描述颜色，还描述场合气质、正式程度和舒适度。
- 穿衣步骤以可选声音辅助保留，但不是进入推荐的前置条件。
- 网络故障、API 故障或文本 AI 故障不能阻断基础演示。

不被允许的假设：

- 不声称已经完成医学色觉或视力诊断。
- 不假设色觉差异只有一种类型，也不声称 AI 知道用户实际看到的颜色。
- 不自动判断衣物实际正反，除非用户完成明确校准。
- 不让文本 AI 自由生成关键穿脱动作。
- 不把“识别到商品”表述为“正品已鉴定”。

## 3. 原功能保留

| 原功能 | v1.0 要求 |
|---|---|
| 自由场合搜索 | 大尺寸搜索框、预设按钮和可选语音输入；本地预设优先 |
| 自动天气 | 作为推荐上下文；不得强制定位，允许演示天气或稍后设置 |
| 我的衣柜 | 本地保存衣物主图；照片、标签、手动和可选语音录入并存 |
| 衣物识别 | 返回可编辑建议；用户确认后保留主图并进入推荐 |
| 标签与商品匹配 | 只返回候选和匹配依据，不做正品鉴定 |
| 三套推荐 | 最多三套；每套包含真实衣物照片、审美摘要、理由和取舍 |
| 单品替换 | 只替换同槽位，更新衣物图片、理由和可选的穿衣计划 |
| 保存今日方案 | 保存 outfit、衣物 ID、场合、来源、完成进度和时间 |
| Mock/Fallback | 推荐、场合解析和穿衣辅助均有本地降级 |
| 公开网页 Demo | 无登录、强依赖后端或真实 AI，可完成同一条核心闭环 |

## 4. P0 冻结范围

两天内必须完成：

1. 黑白高对比首页和可见的图形按钮。
2. 衣柜列表、衣物主图展示和添加衣物入口。
3. 用户拍摄衣物照片，并在本地保存主图。
4. 场合搜索、预设、本地理解和可选语音输入。
5. 表达方向选择：自然、温和、干练。
6. 三套搭配结果；每套必须以用户衣柜照片展示所有主要单品。
7. 方案理由、颜色关系、场合语气、取舍和换鞋。
8. 替换后同步更新照片组合和说明。
9. 确认保存、离线样例和照片缺失状态。
10. 可选语音说明与穿衣顺序作为增强功能保留。
11. 可公开访问的网页镜像和公开源码仓库。

P1 仅在 P0 已稳定后进入：

- 真实相机识别衣物特征。
- OCR 标签和商品候选。
- 真实天气 Provider。
- 文本 AI 生成场合策略和搭配解释。
- 自动部署后端。

P2 不在本次范围：

- 全盲用户拍照建柜流程。
- 医用色觉诊断或色盲矫正建议。
- 连续摄像头观察用户穿衣。
- 自动识别衣物正反而不经用户校准。
- 社交、支付、账户体系。
- 医用或行动安全承诺。

## 5. 主流程

```text
App 进入前台
→ 首页提供“我的衣柜”和场合搜索
→ 打开照片衣柜，选择或添加衣物
→ 输入场合并确认理解
→ 选择“自然 / 温和 / 干练”
→ 生成三套带真实衣物照片的搭配
→ 打开一套查看颜色关系、气质和取舍
→ 点击按钮替换同槽位衣物
→ 确认并保存
```

可选语音辅助：

```text
开启语音
重听
帮助
停止
返回
```

## 6. 图形交互与可选语音

### 6.1 主交互

所有业务步骤必须拥有可见按钮：

- 添加衣物。
- 拍照或从相册选择。
- 保存衣物。
- 生成三套搭配。
- 查看详情。
- 替换单品。
- 确认保存。
- 打开或关闭语音辅助。

按钮必须同时提供图标和文字。选中状态必须有勾选或填充变化，不能只用颜色。

### 6.2 可选语音状态

只有用户主动开启语音辅助时，才进入以下状态：

```text
boot
occasion
confirm
intent
outfits
detail
guide
finish
permissionError
listeningError
```

每个状态必须提供：

- 一个系统问题。
- 一个最小口令集。
- 一个成功转移。
- 一个重听路径。
- 一个无法识别时的收敛提示。

### 6.3 聆听规则

- 原生端使用设备端中文语音识别。
- 只在 App 处于前台且语音会话未结束时聆听。
- 助手朗读时停止识别，避免识别自身回声。
- 助手朗读结束后播放固定双音提示，再自动恢复识别。
- 连续识别结果使用一段静音间隔判定一句话结束，建议 0.9–1.2 秒。
- 已提交的一句话必须清空，不能因识别任务重启而重复执行。
- 后台、锁屏或退出页面后立即停止麦克风和识别任务。
- 不在项目、后端、日志或崩溃报告中保存原始录音。
- 录制权限被拒绝时显示可读屏的阻塞说明和系统设置入口。

### 6.4 口令识别

必须支持同义口令，不要求用户背唯一文案：

| 意图 | 最低支持表达 |
|---|---|
| 开始 | 开始、开始吧、我准备好了 |
| 确认 | 确认、确定、对、是的、可以 |
| 重说 | 重新说、不是、换一个、修改 |
| 自然 | 自然、自然可靠、轻松 |
| 温和 | 温和、温和精致、亲切 |
| 干练 | 干练、清晰、利落 |
| 方案 A/B/C | A、B、C、方案A、第一套 |
| 比较 | 比较、区别、有什么区别 |
| 理由 | 理由、为什么、解释 |
| 换鞋 | 换鞋、替换鞋、换一双鞋 |
| 完成 | 完成、穿好了、下一步 |
| 返回 | 返回、后退、回去、上一步 |

低置信度或无法匹配时只复述当前可选口令，不继续猜测。

## 7. 图片与声音体验

### 7.1 衣物主图

- 每件衣物保存一张本地主图。
- 主图用于衣柜列表、推荐卡片、详情和替换结果。
- 主图缺失时显示 1:1 边框占位和衣物名称。
- 推荐卡片中的图片必须映射到响应里的 item ID。
- iOS 使用本地主图；公开网页使用受许可的样例衣物图片。
- 后端不接收本地图片路径，也不参与最终 UI 图片拼装。

### 7.2 语音输出

- 使用短句，每次只问一个问题。
- 首次摘要建议 8–12 秒，详细理由由用户主动触发。
- 不使用未经解释的视觉词，例如“左图”“右侧卡片”。
- 颜色描述同时解释其气质，例如“浅蓝与深蓝形成清楚但温和的层次”。
- 穿衣动作必须包含衣物、身体位置、一个动作和完成条件。
- 失败提示必须说明下一步能说什么，不能只说“出错了”。

### 7.3 声音语义

```text
左侧短音     用户自己的左侧
右侧短音     用户自己的右侧
上行双音     向上、向前或拿起
下行双音     放下、穿入或完成整理
中央和弦     当前步骤完成
聆听双音     现在可以说话
```

左右声道只是可选穿衣辅助，语音必须同时说出“左侧”或“右侧”。
设备不支持立体声时，图形界面仍能独立完成主流程。

## 8. 穿衣顺序

顺序由客户端确定性规则生成，不由文本 AI 控制。

默认顺序：

```text
下装
→ 上装
→ 配饰
→ 鞋
→ 外套
```

强制依赖：

- 鞋必须在脚部和腿部衣物之后。
- 外套必须在内层上装之后。
- 佩戴配饰不能遮挡或干扰正在使用的行动辅助设备。
- 用户返回上一步时不得丢失当前 outfit。
- 换鞋后必须重新计算穿衣步骤。
- 页面不按计时器自动进入下一步，只有用户说“完成”才推进。

## 9. Apple 视觉要求

视觉目标是 Apple 式的清晰、克制和层级，但把可访问性放在更高优先级。

- 主界面采用黑、白、灰设计，避免低对比的彩色卡片。
- 使用系统字体，支持 Dynamic Type；关键内容适配 200% 字号。
- 关键按钮高度至少 56 pt，图标与文字并列。
- 选中态同时使用描边、填充、勾选和文字，不得只依赖颜色。
- 图标、图片和按钮都要有明确的无障碍标签。
- 三套推荐以照片拼贴作为首要视觉信息，文字作为解释。
- 照片比例统一，边框稳定，避免不同背景影响识别。
- 支持 Dark Mode、VoiceOver、Reduce Motion 和强制高对比度。
- 不要求长按、精细拖拽或辨认无文字图标。
- 公开网页与 iOS 使用同样的黑白基调和照片结果布局。

## 10. 技术结构

### 10.1 iOS

```text
SwiftUI View
  → Wardrobe ViewModel
      → Local Photo Store
      → Garment Recognition Service
  → Recommendation ViewModel
      → Photo Collage Mapper
  → Optional Voice Assistant
  → API Client
      → Local Mock
      → Remote API
```

强制边界：

- View 不直接处理图片识别、推荐排序或语音状态机。
- 衣柜主图由本地模块管理，推荐 DTO 不包含照片路径。
- 图片拼装通过 garment ID 映射到本地衣柜记录。
- 语音服务为可选模块，不得阻断图形主流程。
- 网络层不得依赖 View。
- 推荐网络失败时回到本地 fixture，并显示来源为 fallback。
- 原生版本禁止静默回退到云端语音识别。

### 10.2 后端

- FastAPI。
- 无状态接口优先。
- 外部 AI、天气和搜索必须可替换。
- 推荐接口必须包含规则 fallback。
- Provider Key 只存在于后端环境变量。
- 日志不得记录原始音频、衣物照片、精确坐标或密钥。

### 10.3 公开网页

- 静态 HTML、CSS、JavaScript 优先。
- 不要求构建工具或账户。
- 必须加载同一份样例语义和可公开使用的样例衣物图片。
- 三套推荐展示完整照片卡片，不能退化为纯文字列表。
- 浏览器语音能力不可用时给出真实说明，不伪造成功。
- Web Speech 可能由浏览器使用系统或云服务，必须在披露中说明。

## 11. 数据和接口

推荐请求只包含用户确认后的结构化衣物字段：

```text
id
slot
category
colors
pattern
fit
material
formality_score
warmth_score
user_confirmed
```

禁止在推荐请求中发送：

- 本地照片路径。
- 标签原图。
- 语音录音。
- 精确位置。
- API Key。

客户端保存的本地照片字段：

```text
garment_id
local_photo_path
thumbnail_cache_key
captured_at
```

这些字段只存在于设备，不得加入推荐请求。UI 根据推荐结果中的 `item_ids`
查询本地衣柜，把每件衣物的主图组合成推荐卡片。

共享接口必须先修改 OpenAPI，再修改 sample-data，再通知 iOS，最后联调。
穿衣顺序和可选语音口令由客户端本地生成，不新增共享必填接口字段。

## 12. 隐私与安全

- 麦克风和语音识别权限只在用户主动开启语音辅助时请求，并提供用途说明。
- 原生语音辅助使用设备端识别。
- 助手朗读时暂停识别，离开前台时立即停止。
- 不保存录音、连续语音转写或唤醒历史。
- 衣物原图保存在设备本地。
- 只有用户明确触发图片分析时上传临时压缩图。
- 临时图片不得保存或用于训练。
- 天气定位只在用户启用时使用粗略位置，不建立轨迹。
- 商品 URL 只允许 HTTPS，并防止 SSRF。

## 13. 测试要求

### 13.1 自动化

- 覆盖衣柜照片新增、编辑、删除和本地持久化。
- 覆盖照片缺失时的占位状态。
- 覆盖推荐结果所有 item ID 都能映射到衣柜图片。
- 覆盖三套推荐卡片同时包含图片、标题和理由。
- 覆盖替换后面板图片与 item ID 同步更新。
- 覆盖颜色关系说明、正式程度和取舍字段。
- 覆盖推荐接口失败后的 fallback。
- 覆盖 OpenAPI 样例与客户端 fixture 一致。
- 可选语音开启后，覆盖同义口令、未知口令和自动恢复聆听。

### 13.2 真机

使用实体 iPhone 连续完成三次：

```text
打开照片衣柜
添加一件上装并保存主图
第一次去女朋友家吃饭
确认
自然
查看三套带照片的搭配
打开方案 A
换鞋
确认保存
```

还必须测试：

- 黑白界面在标准、暗色、200% 字号和低视力缩放下可操作。
- 选中、禁用、警告和错误状态不只靠颜色区分。
- 三套搭配照片来自用户衣柜，不是商品图。
- 删除或缺失主图时显示占位和衣物名称。
- 主要按钮至少 56 pt，图标和文字同时可见。
- 扬声器播放时不会自己触发“完成”或“确认”。
- 环境噪声不会触发错误状态。
- 未开启语音时，全部 P0 业务步骤仍可通过图形按钮完成。
- 开启语音后，App 切后台麦克风停止，回前台后可恢复。
- 屏幕锁定、低电量模式和充电时仍可演示。

### 13.3 可用性

至少让一名色弱或色盲用户和一名低视力用户体验一次。观察：

- 是否能分清选中和未选中状态。
- 是否能理解三套搭配的视觉差异。
- 是否能确认推荐使用的是自己的衣物。
- 是否能独立完成添加衣物照片。
- 200% 字号下按钮是否仍可用。

| 第一天结束 | 公开 Demo 地址和可演示版本 |
| 第二天 09:00 | 功能冻结，只修构建、演示和提交阻断 |
| 截止前 1 小时 | 所有链接、海报、披露和四人信息复核 |

## 16. 回报与完成标准

每次交付必须报告：

```text
负责人：
分支：
Commit SHA：
完成模块：
运行设备：
测试命令：
真机操作路径：
照片来源：
实际结果：
截图或录屏：
当前状态：
已知风险：
```

“代码已生成”“AI 说通过”或“看起来没问题”不算完成。完成必须同时满足：

- 有真实 Commit。
- 自动测试通过。
- 有实际请求、真机口令或可访问 URL。
- 共享接口已同步 OpenAPI 和 sample-data。
- 不包含秘密、录音、个人照片或构建产物。
- `docs/build-status.md` 有证据。

## 17. 需求优先级与变更

P0 冻结后，只有以下问题可以插入：

- 构建失败。
- 衣物照片无法添加、显示或映射到推荐。
- 图形按钮、黑白对比或放大后无法操作。
- 核心流程无法完成。
- 公开 Demo 或提交链接不可用。
- 隐私或安全阻断。

新增视觉细节、额外页面、后台唤醒词或新 Provider 一律推迟到 P1/P2。
改变 P0 需要 iOS 负责人、产品负责人和集成协调人共同确认。

## 18. 唯一事实来源

发生冲突时按以下顺序：

```text
1. CONTRIBUTING.md          角色、权限、分支和流程
2. 本文件                    产品范围、图形界面、照片和验收
3. specs/openapi.yaml       接口字段和错误结构
4. specs/examples/sample-data.json
                             固定样例内容
5. design/page-flow.md      页面状态和交互行为
6. docs/build-status.md     当前进度，不是接口事实
```

聊天记录、AI 临时建议和未提交代码不能覆盖以上文件。
